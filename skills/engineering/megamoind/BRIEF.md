# Step 0 research and brief (briefer)

You draft megamoind's step 0 brief; the orchestrator asks the user and writes the answers in. `<skill-dir>` is megamoind's folder, the one holding this file. Write the draft to `<scratchpad>/<ticket>-brief.md`: each item of the round below with its proposal, and which of [`MINIMOI.md`](MINIMOI.md)'s "Eligibility" conditions the ticket meets.

## Research

Fetch the ticket (`gh issue view <n> --json title,body,labels,comments` for a GitHub issue, since its plain output can come back empty in an agent shell; the tracker's tools otherwise); a tracker you can't reach is HITL. Read the ticket and quote each decision in it that the request, or a plan already agreed in the conversation, contradicts: that conflict is HITL. Then read the code it touches as it is on `<base>` (`git show <base>:<file>`, `git grep <pattern> <base>`), since under GitButler the working tree merges every applied branch and its symbols and line numbers may not exist on `<base>`; every `file:line` the brief cites comes from there. Look for what the change can **reuse**: helpers, a similar feature, how the neighbouring tests are written. When the ticket relies on how a third-party service behaves (an embed, a player, an API), read that service's terms or policy for the behaviour and cite it in the plan: a design its terms forbid is HITL before any code. Call the Skill tool with `craftsmanship`. For a bug, call the Skill tool with `diagnosing-bugs` and take it through phase 4, so the plan names the confirmed cause; its fix waits for step 2.

Run `python3 <skill-dir>/scripts/preflight.py --files <paths the plan changes>` once for the repo facts below (default branch, GitButler, CODEOWNERS, required checks, gh version, the sections of each steering file). A path in its `files_in_other_branches` with a branch listed collides with that in-flight branch: the plan names it and proposes basing on that branch or waiting for it.

## The round

With `brief=`, read it and settle on your own whatever of the plan below it leaves open (only the user's decisions are HITL). Otherwise the round asks everything in **one** round, with your proposal for each. When the ticket already states the approach, files and validation, the plan is one short question that restates it and names only where you deviate, with no fallbacks or conditional plans. Each option, and each causal, data or request-flow claim the brief takes from the ticket or an investigation, states only what you checked in code, data or a trace this session, citing the `file:line` or trace line: grep the consumer before claiming "with X, Y happens", reproduce a root cause the ticket states for each case it names, and mark anything unchecked "unverified: …". An option that extends scope to a sibling case ("X has the same bug") quotes the routing line that sends the user's action into that code, found by tracing every call site.

- **Plan**: the approach in a few lines, what it reuses, the seams where tests go with what each buys and sells (Test Desiderata), the tidyings worth doing first or after and where each goes by area of impact (Tidy First), and anything ambiguous in the ticket. When the ticket replaces or reproduces something already visible in the product, the plan keeps its current look, cites the **visual reference** (the screenshot, the live screen), and checks that the shape of the data (copy keys, props) can carry that look, e.g. one copy key can't style half its text.
- **Branch name**: the format in the project's `## Ticket tracker` section, else `<ticket-id>-<short-kebab-description>`, with no `/`. A pre-PR or post-PR from the plan adds `<name>-tidy-first` or `<name>-tidy-after`.
- **Landing**: when the project's `CLAUDE.md` / `CLAUDE.local.md` says changes land without a PR, the run is `stop-at=pushed`; state it in the plan rather than asking.
- **Base** (GitButler): run `but pull --check`. A branch in preflight's `merged_upstream` makes the base stale and blocks commits on the files it touched, so the plan updates before step 2. When the workspace is behind and updating would move other branches, ask: "the workspace is N commits behind; updating would move X and Y. Update?". A no leaves the base stale, so guard against a **borrowed green** (see [`WORKSPACE.md`](WORKSPACE.md)'s "Sharing the workspace").
- **Verification**: how to run the app or service (the dev commands, required env, data or login, ports), and which flows prove the change works, each with its route or entry point and the data it needs. Each observable named as proof (a status, a field, an endpoint's answer, an eval's expected output) cites the handler that produces it (`file:line`) and, when the app runs, has been seen once. Add `keep-env: yes` only when the user asked to keep the environment up after verification; by default the verifier tears it down.
- **CODEOWNERS**: if preflight names one, opening the PR ready for review requests those reviewers automatically. Say so, since it defeats waiting to add reviewers.
- **Required checks**: the names CI must turn green, from the project's `CLAUDE.md` / `CLAUDE.local.md`, else preflight's `required_checks` (the base's rulesets and branch protection; pass `--base <base>` when it isn't the default branch). If neither gives them, or preflight reports `required_checks_error`, ask. Split them into checks that run on drafts and ready-only ones (e.g. a Jenkins job that builds only non-draft PRs whose base is the default branch).
- **Evidence media** (screenshots, recordings): the PR gets them through `gh-attach`, which needs gh ≥ 2.99. When preflight reports `gh_attach_ok: false`, ask the user to upgrade.
- **Ticket description**: ask whether to copy the brief's product decisions (what changes, UI choices, acceptance criteria) into the ticket's description.

Done when every item has a proposal, or a settled answer with `brief=`, and everything needed to reach step 8 without asking again is in the draft.
